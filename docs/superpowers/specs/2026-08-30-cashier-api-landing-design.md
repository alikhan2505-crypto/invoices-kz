# Публичный лендинг Kaspi Cashier API — дизайн

**Дата:** 2026-08-30 (обновлено: добавлены ru+en и интерактивная документация с "Попробовать")
**Новый файл:** `src/app/cashier-api/page.tsx` (публичная маркетинговая страница, без авторизации)
**Переписываемый существующий файл:** `src/app/kaspi-api/docs/page.tsx` — не просто закрывается авторизацией, а заменяется интерактивным OpenAPI-проводником (см. «Интерактивная документация» ниже)
**Новые файлы для документации:** OpenAPI-спека (ru и en) + компонент-обёртка над сторонней библиотекой для рендера (точные пути — в implementation-плане)

## Контекст и цель

Founder вводит Kaspi Cashier API как отдельный продукт для другой аудитории — разработчиков/технических основателей, которым бухгалтерия invoices.kz не нужна вовсе. Ценовой брейнсторм этой же сессии (артефакт «Ценовая архитектура») зафиксировал: аудитория другая → нужна отдельная посадочная страница, отдельный визуальный язык.

Это блокирующая зависимость для отдельного проекта «Редизайн главного лендинга» (спека `2026-08-30-landing-redesign-design.md`), который уже ссылается на маршрут `/cashier-api` в футере и в списке фич — та работа не может быть выполнена, пока эта страница не задеплоена.

## Что уже существует (важно не дублировать)

- **`/kaspi-api`** — авторизованный личный кабинет (подключение Cashier по номеру телефона + смс-код, баланс кошелька, история операций, пополнение). Это НЕ публичная страница — маршрут `/cashier-api` для нового лендинга не конфликтует.
- **`/kaspi-api/docs`** — техническая документация. Сейчас **полностью публична, без какой-либо проверки авторизации** (обычный server-компонент, ни `'use client'`, ни `supabase.auth`, ни редиректа) — любой в интернете может открыть URL напрямую. Контент при этом уже полный и точный (не черновик): быстрый старт на 5 шагов, оба эндпоинта с точными полями, таблица кодов ошибок, полный контракт вебхука и пример верификации подписи на Node.js. Этот контент **переносится** в новую OpenAPI-спеку почти дословно, не переписывается с нуля — переписывается только форма подачи (интерактивный проводник вместо статичного текста) и авторизация доступа.
- **`/api/kaspi/pay`** — `POST`, создание платежа. Заголовок `Authorization: Bearer <api_token>`. Тело `{ amount: number, order_id: string, callback_url?: string }`. Ответ 200: `{ qr_token, payment_link, operation_id, expire_date }`. Rate limit 20 запросов/60 сек на одно подключение. Коды ошибок: `400` (нет обязательных полей), `401` (нет/неверный токен), `402` (не хватает баланса на комиссию), `429` (rate limit), `502` (сбой на стороне Kaspi).
- **`/api/kaspi/pay/status`** — `GET ?operation_id=...`, тот же `Authorization: Bearer <api_token>`. Ответ 200: `{ operation_id, order_id, amount, status, paid }`, где `status` ∈ `pending | paid | expired`. Каждый вызов реально перепроверяет статус у Kaspi (не просто читает БД). Коды ошибок: `401`, `404` (operation_id не найден), `502`.
- **Важно — какие эндпоинты НЕ часть публичного API:** `/api/kaspi/dashboard` и `/api/kaspi/webhook-url` авторизуются **сессией Supabase самого invoices.kz** (`supabaseAuth.auth.getUser(accessToken)`), а не токеном Cashier API — это внутренние эндпоинты страницы `/kaspi-api`, разработчику извне они не нужны и не должны попасть ни в лендинг, ни в OpenAPI-спеку. Публичный API — ровно два эндпоинта выше.
- **Вебхук (не эндпоинт, а исходящий запрос с нашей стороны):** если указан `callback_url`, при успешной оплате мы делаем `POST` на этот URL с телом `{ "event": "payment.success", "order_id", "amount", "operation_id" }` и заголовком `X-Kaspi-Pay-Signature: <hex HMAC-SHA256>`, подписанным собственным `webhook_secret` этого подключения (не общим). `callback_url` обязан быть `https://`, не localhost/приватная сеть — иначе вебхук просто не отправляется.
- **Реальное ценообразование (уже в коде, не гипотеза):** `COMMISSION_RATE = 0.02` в `src/lib/kaspiPay/wallet.ts` — 2% с суммы каждого **проведённого** платежа, из предоплаченного баланса (`kaspi_wallet_balance` в `profiles`). Подключение Cashier само по себе бесплатно на любом тарифе. Никакой абонентской платы и минимального оборота.

## Решение о цене (принято в этом брейнсторме)

Рекламировать **уже живую** модель — 2% с оплаченного, без абонплаты. НЕ рекламировать гипотетический «5–10₸/вызов» из ценового меморандума — та модель не реализована в коде, и вводить её сейчас означает сначала строить новый биллинг, а не только лендинг. Если объём вырастет настолько, что понадобится другая модель — это отдельное решение в будущем, не часть этого проекта.

## Решение о раскрытии механизма (принято в этом брейнсторме)

Kaspi официально не даёт публичного merchant API для этого сценария — Cashier работает через тот же неофициальный протокол, что и приложение Kaspi Pay Cashier. Founder явно не хочет, чтобы конкуренты могли по документации воспроизвести сервис.

- **Лендинг** (`/cashier-api`): шаг подключения формулируется на уровне «номер телефона + смс-код, как в приложении Kaspi Pay» — этого достаточно для доверия и понимания, не раскрывает протокол. Никакого отдельного риск-дисклеймера на самой странице не нужно.
- **`/kaspi-api/docs`**: закрыть от посторонних — та же проверка авторизации, что уже используется на `/kaspi-api` (клиентская проверка сессии через `supabase.auth.getUser()`, редирект на `/login` при отсутствии сессии). Технические детали (включая интерактивный «Попробовать», см. ниже) видны только вошедшим пользователям, не любому в интернете.
- **Мягкое упоминание риска (изначальное решение брейнсторма, до уточнения про закрытие доков):** раз доки теперь видны только вошедшим реальным клиентам, а не любому в интернете, короткая честная заметка уместна именно здесь — один абзац в конце OpenAPI-страницы (или в отдельном коротком блоке FAQ на ней) вида «Это не официальный Kaspi merchant API — интеграция сделана по тому же принципу, что и мобильное приложение Kaspi Pay Cashier. Мы поддерживаем совместимость и уведомим вас, если Kaspi изменит свою сторону.» Без технических деталей протокола — только честность перед уже зашедшим клиентом, не инструкция для копирования конкурентом.

- Утверждено визуально через visual companion (`hero-docs-refined.html`, `full-page-v1.html`) — направление "docs-first с вкладками языков" (вариант C из трёх предложенных), а не терминал-геро на весь экран (A) и не сплит с QR-иллюстрацией (B).

## CTA-поведение

Обе кнопки «Получить доступ к API» (в hero и в финальном CTA) ведут на `/login` — **то же поведение**, что у всех CTA основного лендинга (`goLogin` → `router.push('/login')` в `page.tsx`). У `/login` сейчас нет параметра редиректа после входа (проверено — `redirectTo` в коде `/login` жёстко указывает на `/auth/callback`, без поддержки `next=`), так что после входа пользователь попадает на дефолтный пункт назначения входа (не обязательно `/kaspi-api`) — это существующее ограничение инфраструктуры входа, чинить его не входит в объём этого проекта. Кнопка «Смотреть документацию» ведёт на `/kaspi-api/docs`.

## Локализация

**Русский и английский**, оба обязательны (founder explicitly, 2026-08-30) — казахский НЕ включён в этот проект (не запрашивался). Это касается ОБОИХ поверхностей: лендинга `/cashier-api` и интерактивной документации `/kaspi-api/docs`.

- **Лендинг** (`/cashier-api`): та же схема, что в `src/app/page.tsx` — объект `COPY` с ключами `ru`/`en`, переключатель языка в header (переиспользовать `useLanguage()`/`LanguageProvider`, уже используемые по всему проекту — не изобретать свой механизм языка для одной страницы).
- **Документация** (`/kaspi-api/docs`): OpenAPI-спека пишется в ДВУХ версиях контента — `openapi.ru.json` и `openapi.en.json` (одинаковая структура/эндпоинты, разные `summary`/`description`/`example`-строки) — переключатель языка на странице подгружает нужный файл в компонент-рендерер.
- **Известное ограничение (честно фиксируем сейчас, а не как сюрприз в реализации):** готовые библиотеки интерактивных OpenAPI-проводников (Scalar, Swagger UI, RapiDoc и т.п.) обычно НЕ локализуют собственный интерфейсный текст (слова вроде "Try it", "Response", "Authorize" на кнопках самого инструмента) — только содержимое спеки (наши описания, примеры) можно перевести, потому что этот текст — наш. Небольшое количество английских слов-лейблов интерфейса остаются английскими даже в русском режиме, если выбранная библиотека не имеет собственного i18n. Implementation-план должен явно проверить, поддерживает ли выбранная библиотека локализацию чистого UI, и если нет — явно сообщить об этом ограничении, а не молча оставить страницу наполовину на английском без объяснения.

## Интерактивная документация («Попробовать») — замена `/kaspi-api/docs`

Пример, который дал founder: **xpayment.kz/docs** — полноценный OpenAPI-проводник (проверено вживую через браузер 2026-08-30): переключатель RU/KZ/EN и тёмной темы, кнопка «Авторизовать» с полем для токена, каждый эндпоинт — сворачиваемая карточка с полями параметров (предзаполненные примеры), вкладки языка кода (curl/Go/Python), кнопка «Попробовать», которая делает **реальный** запрос к их продакшн-API текущим введённым токеном, и панель «ОТВЕТ» с живым JSON.

Наша версия — тот же паттерн, поверх реального (не выдуманного) API-контракта из раздела «Что уже существует» выше:

### Объём API-поверхности

Ровно два эндпоинта — `POST /api/kaspi/pay` и `GET /api/kaspi/pay/status`. Никакие другие `/api/kaspi/*` роуты не документируются как публичные (они либо внутренние, либо не относятся к Cashier).

### OpenAPI-спека

Новый файл(ы) — например `src/lib/kaspiCashierApi/openapi.ru.json` и `openapi.en.json` (OpenAPI 3.0 или 3.1, конкретная версия — на усмотрение реализации в зависимости от требований выбранной библиотеки-рендерера). Содержимое переносится из существующего `src/app/kaspi-api/docs/page.tsx` (см. «Что уже существует» — это не новый текст, а перевод уже проверенного контента в формат OpenAPI):
- Оба эндпоинта с точными полями запроса/ответа, каждое поле — с описанием (`required`/`optional`, тип, пример значения) как в существующей странице.
- Таблица кодов ошибок (401/400/402/404/429/502) — как `responses` для каждого эндпоинта.
- Секция вебхука — OpenAPI 3.1 поддерживает `webhooks` как отдельный раздел спеки; если выбранная библиотека не рендерит `webhooks` из коробки, вебхук документируется отдельным статичным блоком на той же странице (payload `payment.success`, заголовок `X-Kaspi-Pay-Signature`, пример верификации на Node.js — переносится дословно из текущей страницы).
- `securitySchemes`: `bearerAuth` (`Authorization: Bearer <api_token>`) для обоих эндпоинтов.

### Библиотека-рендерер

Implementation-план выбирает конкретную библиотеку (кандидаты: `@scalar/api-reference-react`, `swagger-ui-react`, RapiDoc как web component) по критериям: (1) реальная кнопка "Try it" с живым запросом к нашему собственному хосту (не через сторонний прокси — вызовы должны идти напрямую с браузера пользователя на `https://www.invoices.kz/api/kaspi/pay`, никогда не через сервер библиотеки), (2) поддержка тёмной темы с кастомизируемой палитрой (переиспользовать `#0a0c10`/`#0d1117`/`#161b22`/`#c9d1d9`/`#7ee787`/`#238636` из лендинга — визуальная консистентность между `/cashier-api` и `/kaspi-api/docs`), (3) генерация примеров кода на нескольких языках из самой спеки (минимум curl/JavaScript/Python, как на лендинге).

### Поток авторизации внутри страницы

Два независимых уровня, не путать:
1. **Доступ к самой странице** — сессия invoices.kz (см. «Решение о раскрытии механизма» выше) — без входа вообще не открывается, редирект на `/login`.
2. **Кнопка "Авторизовать" внутри проводника** — пользователь вставляет свой РЕАЛЬНЫЙ Cashier API-токен (тот, что получил на `/kaspi-api`) в поле библиотеки. Токен живёт только в браузере (стандартное поведение этих библиотек — держат его в памяти/localStorage вкладки, никогда не уходит на сервер invoices.kz кроме как в заголовке `Authorization` самого тестового запроса). "Попробовать" на эндпоинте создания платежа делает **настоящий** платёж (это не sandbox — у Kaspi Pay нет тестового режима) — со страницы должно быть явно видно (короткая заметка над кнопкой), что вызов реальный и спишет комиссию при оплате, аналогично тому, как это устроено на xpayment.kz.

## Технические детали реализации

- Новый файл `src/app/cashier-api/page.tsx` — можно НЕ быть `'use client'` целиком, если язык/вкладки реализованы как отдельные клиентские острова (`useState` в подкомпонентах), но раз теперь используется `useLanguage()` (общий контекст-провайдер), она в любом случае должна быть `'use client'`, как и `src/app/page.tsx`.
- Framer-motion не обязателен (в отличие от основного лендинга) — это более сдержанная, docs-подобная страница; лёгкие CSS-transition для наведения на кнопки достаточно. Если используется анимация появления секций при скролле — обязательно с `prefers-reduced-motion` guard, как везде в проекте.
- Тач-таргет 44px — та же база проекта, что применена в остальных недавних правках (`a42a67b`, `366074b`) — обе CTA-кнопки, вкладки языка кода и переключатель RU/EN должны соответствовать.
- Изменение `src/app/kaspi-api/docs/page.tsx`: полная замена содержимого на компонент интерактивного проводника (см. выше), обёрнутый в ту же авторизационную проверку, что в `src/app/kaspi-api/page.tsx:96-98` (`'use client'`, `useEffect` + `supabase.auth.getUser()`, редирект на `/login`, короткий лоадер `Загрузка…` пока идёт проверка).

## Границы (что НЕ входит)

- Изменение реальной модели биллинга (переход на «5–10₸/вызов» или любую другую) — не в этом проекте.
- Редирект-параметр (`next=`) для `/login` — существующее ограничение, не чинится здесь.
- Казахская версия — не запрашивалась, не входит (в отличие от английской, которая обязательна).
- Любые изменения `/kaspi-api` (личный кабинет) кроме `/kaspi-api/docs` — не трогаем.
- Ежегодная подписка / изменения `settlePlanPayment.ts` — не относится к этому проекту.
- Настоящий sandbox/тестовый режим для Kaspi Pay (отдельная система без реальных денег) — не существует и не строится в этом проекте; "Попробовать" в доках всегда бьёт по реальному API.
