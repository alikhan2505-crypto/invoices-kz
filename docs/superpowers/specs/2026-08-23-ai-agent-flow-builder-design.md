# AI-агент — визуальный конструктор сценариев (Telegram v1) — Design

**Status:** approved section-by-section with the user in live dialogue (2026-08-23), each section confirmed before moving to the next.

## Обзор

AI-агент сейчас умеет отвечать клиенту двумя способами: точное совпадение по ключевому слову с готовым шаблоном (бесплатно), или ИИ-ответ (платно, 1 кредит/5₸). Конкурентная разведка 22.08 (см. `[[competitor_research_kaspibot_aiagent_invoices_kz]]`) нашла у Kelesu третий, недостающий у нас режим: визуальный **не-ИИ конструктор сценариев** — заранее прописанное дерево «сообщение → кнопки → следующее сообщение», дешевле в эксплуатации (бесплатно, как шаблон) и предсказуемее ИИ для типовых задач — меню, FAQ, запись.

**v1 — только Telegram.** У Telegram самые гибкие inline-кнопки (до 8 в ряд, любое число рядов) — проще всего доказать концепцию там, расширять на WhatsApp/Instagram с учётом их более узких лимитов (WhatsApp — максимум 3 кнопки или список до 10 пунктов) — отдельная будущая итерация, не в этом плане.

## Модель данных

Новая таблица:

```sql
create table ai_agent_flows (
  id uuid primary key default gen_random_uuid(),
  agent_id uuid not null references ai_agents(id) on delete cascade,
  name text not null default 'Новый сценарий',
  trigger_words text[] not null default '{}', -- вход в сценарий по ключевому слову, та же логика matching, что и у шаблонов
  is_start boolean not null default false, -- этот сценарий запускает /start вместо статичного приветствия
  definition jsonb not null default '{"steps":[]}', -- весь граф шагов одним документом
  created_at timestamptz not null default now()
);

-- Не больше одного "главного" сценария на агента.
create unique index ai_agent_flows_one_start_per_agent
  on ai_agent_flows (agent_id) where is_start;
```

**Форма `definition`:**

```json
{
  "steps": [
    {
      "id": "step_1",
      "text": "Здравствуйте! Что вас интересует?",
      "buttons": [
        { "label": "Узнать цены", "nextStepId": "step_2" },
        { "label": "Как сделать заказ", "nextStepId": "step_3" }
      ]
    },
    {
      "id": "step_2",
      "text": "Актуальные цены смотрите на сайте: ...",
      "buttons": []
    }
  ]
}
```

Первый элемент массива `steps` — стартовый шаг сценария. `buttons: []` (пустой массив) у шага — терминальный: после отправки этого шага сценарий считается завершённым, состояние клиента сбрасывается.

**`ai_agent_conversations` получает два новых nullable-столбца:** `active_flow_id uuid references ai_agent_flows(id)`, `active_step_id text` (id шага внутри `definition.steps`, не отдельная таблица/FK — id шага существует только внутри JSON-документа конкретного сценария).

## Приоритет обработки входящего сообщения (Telegram)

Порядок проверок при получении любого апдейта от клиента:

1. **Клиент внутри сценария (`active_flow_id` не null) и апдейт — `callback_query`** → обработка внутри сценария (см. ниже), template match и ИИ не вызываются.
2. **Клиент внутри сценария, но апдейт — обычный текст** → сценарий немедленно завершается (`active_flow_id`/`active_step_id` сбрасываются в null), сообщение обрабатывается штатно с шага 3 — **никакого «пожалуйста, нажмите кнопку»**: если клиент предпочитает печатать, а не жать кнопки, ИИ должен ответить по существу, а не заставлять его вернуться в меню.
3. **Клиент не в сценарии** → поиск по шаблонам (`findTemplateMatch`, без изменений) — существующее поведение и приоритет шаблонов над всем новым не меняются.
4. **Шаблон не найден** → проверка триггер-слов всех сценариев агента (`trigger_words`, та же функция сопоставления, что и у шаблонов) — совпало → сценарий запускается (см. ниже).
5. **Ничего не совпало** → ИИ-ответ, как сейчас, без изменений.

`/start` — особый случай, идёт даже раньше шага 1 (как и сейчас): если у агента есть `is_start`-сценарий — запускается он вместо статичного `"Здравствуйте! Напишите ваш вопрос — я на связи."`; если нет ни одного `is_start`-сценария — поведение `/start` не меняется вообще.

## Telegram-механика

**Новый вид апдейта в `parseTelegramUpdate`** (`src/lib/aiAgent/telegram.ts`): `{ kind: 'callback_query', chatId, data, callbackQueryId, fromHandle }` — сейчас `callback_query` полностью маршрутизируется в `{kind:'ignore'}`, эта ветка распознаётся отдельно.

**Формат `callback_data`:** Telegram ограничивает это поле 64 байтами. Не кодируем туда `flowId`/`stepId` — сервер и так знает текущий шаг клиента из `ai_agent_conversations.active_flow_id`/`active_step_id`. `callback_data` — просто индекс нажатой кнопки в массиве `buttons` текущего шага: `"btn:0"`, `"btn:1"`, …

**Отправка шага:** новая функция в `telegram.ts`, отправляющая текст шага с `reply_markup: { inline_keyboard: [[{text, callback_data}], ...] }` — один ряд на кнопку (простейшая раскладка для v1, без попытки паковать несколько кнопок в один ряд).

**`answerCallbackQuery` обязателен:** без него у клиента до таймаута крутятся «часики» на нажатой кнопке. Новая `answerTelegramCallbackQuery(botToken, callbackQueryId): Promise<void>` — вызывается сразу по получении `callback_query`, до отправки следующего шага.

**Обработка клика:** индекс из `callback_data` → находим кнопку в `buttons` текущего (`active_step_id`) шага → её `nextStepId`. Два разных терминальных случая, оба сбрасывают `active_flow_id`/`active_step_id` в null, но по-разному:
- **`nextStepId` указывает на существующий id шага** — обновляем `active_step_id`, отправляем текст и кнопки этого шага. Если у ЭТОГО шага `buttons: []` — он терминальный: сразу после отправки его текста сбрасываем состояние (следующего клика не ждём).
- **`nextStepId === null`** — сценарий завершается немедленно, **без отправки дополнительного сообщения** (кнопка со своим лейблом, например «Готово ✅», уже была финальным сообщением для клиента) — сразу сбрасываем состояние.
- **Индекс из `callback_data` не найден среди кнопок текущего шага** (устаревшее нажатие на давно отправленное сообщение после смены сценария/шага) — отвечаем `answerCallbackQuery` с текстом-уведомлением («Этот сценарий уже неактуален») и ничего больше не делаем.

## Биллинг

Прохождение по сценарию — **бесплатно**, как совпадение по шаблону: ни ИИ-вызов, ни списание с кошелька. Это и есть смысл фичи по итогам разведки конкурентов — дешевле в эксплуатации, чем токены ИИ.

## API

**Новый CRUD-роут `/api/ai-agent/flows`**, зеркалит уже существующий `/api/ai-agent/templates/route.ts`:
- `GET ?agentId=...` — список сценариев агента.
- `POST` — создать (без `id` в теле) или обновить (`id` в теле) сценарий; тело — весь объект целиком, включая полный `definition`. Никакого API на отдельные шаги — редактор всегда шлёт документ разом.
- `DELETE ?id=...` — удалить сценарий.

Установка `is_start: true` на одном сценарии в этом же запросе должна снять флаг с прежнего (если был) — делается транзакционно на сервере (два `update`, оба под одним запросом), а не понадеявшись на клиент прислать оба изменения.

## UI — вкладка «Сценарии»

Новая вкладка в `/ai-agent/settings` (`?tab=flows`), рядом с уже существующей «Шаблоны», тот же визуальный язык (карточки `nav-glass`).

- Список сохранённых сценариев агента — имя + бейдж «Главный» у `is_start`-сценария.
- Билдер выбранного сценария — вертикальный список карточек-шагов (линейный шаг-за-шагом редактор, не canvas):
  - Текстовое поле сообщения шага.
  - Список кнопок: текст кнопки + выпадающий список «куда ведёт» (любой другой шаг этого сценария, или «Конец сценария» = `nextStepId: null`).
  - «+ Добавить кнопку» / «+ Добавить шаг».
  - Удаление шага: если на удаляемый шаг ссылается кнопка другого шага — эта ссылка автоматически сбрасывается на «Конец сценария» (не оставляем битую ссылку в `definition`).
- Поле триггер-слов сценария (тот же UI-паттерн, что у шаблонов).
- Переключатель «Запускать по /start» — включение на одном сценарии на клиенте сразу выключает его у прежнего главного (UI отражает будущий серверный swap до ответа API, оптимистично).

**Тестовый чат (`TestChatPanel`) не трогаем.** Он сейчас работает только с текстовым ИИ-пайплайном и не умеет отрисовывать кнопки — тестирование сценария в v1 только вживую в реальном Telegram.

## Явно не входит в объём v1

- WhatsApp/Instagram-каналы для сценариев — только Telegram.
- Захват свободного текста внутри шага сценария (например, «оставьте номер телефона» с последующим парсингом ответа) — шаги v1 только с кнопками, никакого текстового ввода как часть сценария.
- Переход между разными сценариями — кнопка одного сценария не может вести на шаг другого сценария.
- Аналитика прохождения (сколько клиентов дошло до конца, где чаще всего отваливаются).
- Импорт/экспорт сценариев между агентами.
- Отрисовка кнопок в `TestChatPanel`.

## Тестирование

По уже принятому в проекте правилу: сетевые вызовы (Telegram `answerCallbackQuery`, отправка шага) без тестов. Чистая логика — `parseTelegramUpdate`'s новая `callback_query`-ветка, поиск кнопки по индексу, определение терминальности шага — получает colocated-тесты, тем же файлом (`telegram.test.ts`), что и вся остальная логика разбора апдейтов.
