# Витрина именных 3D-брелков — Design

## Context

Founder лично владеет 3D-принтером и печатает/продаёт изделия на заказ (сейчас — вручную, по переписке). Хочет публичную витрину-конфигуратор по образцу параметрических инструментов вроде MakerWorld MakerLab (`Name_Keychain_Font_Basic.scad`): клиент настраивает форму/шрифт/цвет/текст, видит живой 3D-предпросмотр, оформляет и оплачивает заказ сам.

Это **личный магазин founder'а**, не новая фича платформы invoices.kz для всех продавцов (решено в брейншторме) — architecture проще: без мультитенантности, без привязки к обычным продавцам/`invoices`.

Брейншторм 05.10.2026 закрыл все развилки:
- Кто продаёт: только founder, его собственный 3D-принтер.
- Предпросмотр: настоящая 3D-модель (не плоский макет), крутится мышкой.
- Каталог: только один товар — именной брелок — сейчас. Архитектура не мешает добавить второй товар позже, но его не строим.
- Цвет: ДВА независимых цвета — основа и текст (контрастная надпись, как печатает большинство таких брелков).
- Оплата: Kaspi Pay прямо на сайте, переиспользуем готовую интеграцию (см. `src/lib/kaspiPay/` и Kaspi Shop × Kaspi Pay мост, `kaspi_shop_repricer_invoices_kz` память).
- Уведомление о заказе: Telegram, тем же каналом (`sendTelegramNotification`, `src/lib/telegramNotify.ts`), что уже использует планировщик записей.
- Цвета филамента (реальный список founder'а): белый, чёрный, серый, жёлтый, зелёный, красный, бордовый.
- Размещение: отдельный путь `/print` на apex `invoices.kz` (не поддомен — не усложняем ещё одним DNS-шагом ради личного проекта).

## Поток целиком

1. Гость открывает `/print` (без входа).
2. Настраивает брелок: форма → шрифт → текст → цвет основы → цвет текста → размер. Справа/снизу — живая 3D-модель, крутится мышкой (orbit), обновляется на каждое изменение параметра.
3. Видит цену (считается от размера), жмёт «Заказать».
4. Короткая форма: имя получателя, телефон, (опционально) комментарий к заказу.
5. Переход на Kaspi Pay (ровно та же схема счёта/оплаты, что уже использует Kaspi Shop — см. `src/lib/kaspiPay/`), оплата.
6. Webhook подтверждает оплату → `print_orders.status` переходит в `paid` → **на сервере генерируются 2 STL-файла** (основа отдельно, текст отдельно — так удобно назначить два цвета в слайсере для мультиматериального принтера) из тех же параметров, что были в конфигураторе → сохраняются в Supabase Storage.
7. Founder получает Telegram-уведомление: кто заказал, параметры, ссылки на оба STL.
8. Печать/доставка — вручную, как сейчас. Никакого отслеживания статуса доставки в v1 (YAGNI — founder сам знает, что печатает).

## Конфигуратор — параметры

- **Форма основы** (5, фиксированный список на старте): скруглённый прямоугольник, овал, сердце, звезда, круг. У каждой — маленькое отверстие под кольцо в одном и том же относительном месте.
- **Шрифт** (4, все с кириллицей и достаточно толстым начертанием, чтобы не ломаться при печати): PT Sans Bold, Unbounded Bold, Caveat Bold, Golos Text Bold.
- **Текст** — произвольная строка (имя), до 20 символов (простая валидация формы). Кегль текста всегда авто-масштабируется под ширину выбранной формы — короткое имя крупнее, длинное мельче, но всегда помещается; никакого отдельного предупреждения "не влезет" не нужно.
- **Цвет основы / Цвет текста** — независимые селекторы, оба из одного списка: белый, чёрный, серый, жёлтый, зелёный, красный, бордовый. Цвет в конфигураторе влияет только на материал 3D-превью (не на геометрию) — чисто визуальный выбор филамента.
- **Размер** — S / M / L, масштабирует всю геометрию и меняет цену.

## 3D-технология

**Three.js** (новая npm-зависимость `three`), геометрия строится процедурно прямо в коде — НЕ OpenSCAD/WASM, НЕ повторяет движок MakerWorld 1:1:
- Форма-основа: `THREE.Shape` (контур формы) → `THREE.ExtrudeGeometry` (толщина).
- Текст: `THREE.TextGeometry` из предзагруженного typeface-JSON шрифта (three.js собственный формат, не обычный .ttf/.woff) — приподнят над основой, не вырезан (рельефная надпись, не гравировка — так печатает подавляющее большинство подобных брелков, проще и прочнее физически).
- Цвет — обычный `MeshStandardMaterial` per-mesh, отдельно на основу и на текст.

**Общий чистый модуль геометрии**, используется в двух местах:
- Клиент: `@react-three/fiber` + `@react-three/drei` (тонкая декларативная обёртка над тем же three.js — `OrbitControls`, упрощённая загрузка шрифта) — живой WebGL-предпросмотр в браузере.
- Сервер: тот же модуль геометрии (plain three.js, без React) вызывается в API-роуте после успешной оплаты, чтобы детерминированно построить STL из сохранённых параметров заказа — клиентской геометрии не доверяем (могла быть подделана), пересобираем с нуля на сервере из того, что реально записано в `print_orders`.
- Экспорт: `THREE.STLExporter` (из `three/examples/jsm/exporters/STLExporter.js`) — сериализация геометрии в STL не требует WebGL/canvas, штатно работает в Node.

**Шрифты — одноразовая подготовка ассетов.** 4 выбранных Google Fonts (кириллица, жирное начертание) нужно один раз конвертировать в typeface-JSON (скрипт на `opentype.js`, по образцу facetype.js) и положить статикой в репозиторий — не генерируется на лету, не требует сети в рантайме.

## Данные

```sql
create table public.print_orders (
  id uuid primary key default gen_random_uuid(),
  status text not null default 'pending' check (status in ('pending','paid','failed')),
  shape text not null,
  font text not null,
  text text not null,
  base_color text not null,
  text_color text not null,
  size text not null check (size in ('S','M','L')),
  price int not null,
  customer_name text not null,
  customer_phone text not null,
  note text,
  kaspi_payment_request_id uuid,
  base_stl_path text,
  text_stl_path text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Та же поза RLS-без-политик, что у `salon_sites`/`planner_sessions` — доступ только через service-role внутри роутов. Это не привязано ни к `profiles`, ни к обычным продавцам — чисто личный журнал заказов founder'а; авторизация админских экранов (если понадобится список заказов позже) — обычный `requireAdmin()`/`is_admin`, тот же паттерн, что у генератора сайтов салонов.

**Платёж.** Переиспользуем существующую интеграцию Kaspi Pay (`src/lib/kaspiPay/`) — создаём платёжный запрос тем же механизмом, что уже работает у Kaspi Shop × Kaspi Pay моста, `kaspi_payment_request_id` на `print_orders` ссылается на существующую таблицу `kaspi_payment_requests`. Webhook, который уже обрабатывает подтверждение оплаты Kaspi Pay, получает новую ветку: по типу/источнику запроса находит `print_orders` вместо обычного счёта и переводит его в `paid` + запускает генерацию STL.

## Цены (черновик, можно поменять одной строкой — простая константа, не поле в БД и не админ-UI в v1)

- S (~5 см): 2500 ₸
- M (~7 см): 3500 ₸
- L (~9 см): 4500 ₸

## Вне рамок v1 (явно)

- Второй и далее товар (таблички, фигурки) — архитектура не мешает, но не строится сейчас.
- Отслеживание статуса печати/доставки.
- Многоцветный текст (больше одного цвета на надпись) или градиенты.
- Гравировка вместо рельефа.
- Произвольная загрузка своего шрифта/логотипа клиентом.
- Публичный список заказов founder'а (кроме Telegram-уведомления) — если понадобится, добавляется позже отдельной маленькой фичей поверх уже существующей таблицы.
