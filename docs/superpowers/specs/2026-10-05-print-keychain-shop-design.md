# Витрина именных 3D-брелков — Design

## Context

Founder лично владеет 3D-принтером и печатает/продаёт изделия на заказ (сейчас — вручную, по переписке). Хочет публичную витрину-конфигуратор по образцу параметрических инструментов вроде MakerWorld MakerLab (`Name_Keychain_Font_Basic.scad`): клиент настраивает форму/шрифт/цвет/текст, видит живой 3D-предпросмотр, оформляет и оплачивает заказ сам.

Это **личный магазин founder'а**, не новая фича платформы invoices.kz для всех продавцов (решено в брейншторме) — architecture проще: без мультитенантности, без привязки к обычным продавцам/`invoices`.

Брейншторм 05.10.2026 закрыл все развилки:
- Кто продаёт: только founder, его собственный 3D-принтер.
- Предпросмотр: настоящая 3D-модель (не плоский макет), крутится мышкой.
- Каталог: только один товар — именной брелок — сейчас. Архитектура не мешает добавить второй товар позже, но его не строим.
- Цвет: ДВА независимых цвета — основа и текст (контрастная надпись, как печатает большинство таких брелков).
- Оплата: Kaspi Pay прямо на сайте, переиспользуем готовую интеграцию (см. `src/lib/kaspiPay/` и Kaspi Shop × Kaspi Pay мост, `kaspi_shop_repricer_invoices_kz` память).
- Уведомление о заказе: Telegram, тем же каналом (`sendTelegramNotification`, `src/lib/telegramNotify.ts`), что уже использует планировщик записей.
- Цвета филамента (реальный список founder'а): белый, чёрный, серый, жёлтый, зелёный, красный, бордовый.
- Размещение: отдельный путь `/print` на apex `invoices.kz` (не поддомен — не усложняем ещё одним DNS-шагом ради личного проекта).

**Изучили сам референс вживую 05.10.2026** (founder открыл сессию MakerWorld MakerLab, до этого был виден только публичный текст страницы модели без конфигуратора) и пересмотрели два пункта по итогам:
- **Форма — не выбор из готовых фигур.** У референса нет селектора "сердце/звезда/круг": основание — это автоматический контур вокруг самого текста с отступом (их параметр `border size`), со скруглением углов и заделкой внутренних дырок у букв типа "о"/"а". Каждое имя получает уникальный силуэт. Переняли этот подход вместо изначально предложенных 5 фиксированных фигур — проще реализовать и персональнее выглядит.
- **Шрифтов не 4, а целый каталог Google Fonts (8267, с поиском)** — у референса это `font_name` с модалкой-пикером. Полный каталог не нужен (там нет кириллицы в большинстве), но расширили с 4 до ~20-25 кириллических шрифтов с поиском — технически реально через живой парсинг шрифта в браузере (`opentype.js`), не через предзаготовленную конвертацию каждого шрифта заранее (см. ниже).

## Поток целиком

1. Гость открывает `/print` (без входа).
2. Настраивает брелок: текст → шрифт (поиск по списку) → цвет основы → цвет текста → размер. Справа/снизу — живая 3D-модель, крутится мышкой (orbit), пересчитывается мгновенно на каждое изменение (не через кнопку "Generate" с задержкой, как у референса — наша геометрия достаточно простая для честного реал-тайма прямо в браузере).
3. Видит цену (считается от размера), жмёт «Заказать».
4. Короткая форма: имя получателя, телефон, (опционально) комментарий к заказу.
5. Переход на Kaspi Pay (ровно та же схема счёта/оплаты, что уже использует Kaspi Shop — см. `src/lib/kaspiPay/`), оплата.
6. Webhook подтверждает оплату → `print_orders.status` переходит в `paid` → **на сервере генерируются 2 STL-файла** (основа отдельно, текст отдельно — так удобно назначить два цвета в слайсере для мультиматериального принтера) из тех же параметров, что были в конфигураторе → сохраняются в Supabase Storage.
7. Founder получает Telegram-уведомление: кто заказал, параметры, ссылки на оба STL.
8. Печать/доставка — вручную, как сейчас. Никакого отслеживания статуса доставки в v1 (YAGNI — founder сам знает, что печатает).

## Конфигуратор — параметры

- **Текст** — произвольная строка (имя), до 20 символов (простая валидация формы).
- **Шрифт** — ~20-25 кириллических Google Fonts, с полем поиска по названию (та же механика, что у референса, просто меньший курированный список). Отбираем достаточно толстые/округлые начертания, чтобы не ломались при печати мелким текстом — без тонких засечек и волосяных линий.
- **Цвет основы / Цвет текста** — независимые селекторы, оба из одного списка: белый, чёрный, серый, жёлтый, зелёный, красный, бордовый. Влияет только на материал 3D-превью (не на геометрию) — визуальный выбор филамента.
- **Размер** — S / M / L, масштабирует всю геометрию и меняет цену.

Фиксированные (не вынесены в UI, чтобы не перегружать клиента техническими миллиметрами — референс даёт их настраивать, но founder просил ровно "форма/шрифт/цвет/надпись", этого достаточно): толщина основы, толщина рельефного текста, ширина обводки-контура, радиус скругления углов, размер отверстия под кольцо — всё как разумные константы на размер (S/M/L), по образцу значений по умолчанию у референса (база 2мм, текст +1.4мм, обводка ~3.4мм, кольцо ⌀5мм/стенка 3мм).

Одно небольшое добавление сверх исходного плана, но от референса — **кольцо можно ставить в начало или в конец имени** (чекбокс `ringAtEnd`), дёшево и заметно улучшает вид для разных по длине имён.

## 3D-технология

Вместо фиксированных фигур (как планировалось до просмотра референса) — **автоконтур вокруг текста**, 1:1 идея референса, но собственная реализация без OpenSCAD/WASM:

1. **Контуры букв.** `opentype.js` разбирает шрифт (TTF, см. ниже) и отдаёт реальные векторные контуры каждой буквы набранного текста — готовый, проверенный способ (та же библиотека лежит в основе инструментов вроде facetype.js, которым сделаны typeface-шрифты самого three.js).
2. **Контур основы.** Контуры букв (может быть несколько несвязанных фигур — буквы отдельно) идут в `clipper-lib` (JS-порт классической библиотеки Clipper для булевых операций и offset/inset над 2D-полигонами) — одна операция "outset на N мм, со скруглёнными углами" сразу даёт и объединение близких букв в плавный контур, и скругление (без отдельного шага), и исходный силуэт "обводка вокруг имени", который видно на референсе.
3. **Кольцо.** Небольшое кольцо-отверстие с короткой перемычкой к основному контуру добавляется в тот же набор полигонов до шага offset, чтобы перемычка получилась органичной частью контура, а не приклеенным сверху кружком.
4. **Три геометрии в three.js:** контур основы → `THREE.ExtrudeGeometry` (толщина основы); контуры букв (неоффсетнутые) → `THREE.ExtrudeGeometry` (толщина текста, приподняты над основой — рельеф, не гравировка, так печатает подавляющее большинство подобных брелков); кольцо — вырез в основе (`THREE.Shape` с `holes`).
5. Цвет — `MeshStandardMaterial` per-mesh, отдельно на основу и на текст.

**Общий чистый модуль геометрии** (принимает `{text, font, ringAtEnd, size}`, отдаёт три `THREE.BufferGeometry`), используется в двух местах:
- Клиент: `@react-three/fiber` + `@react-three/drei` (тонкая декларативная обёртка над тем же three.js — `OrbitControls`) — живой WebGL-предпросмотр, пересчёт на каждое изменение параметра (геометрия простая, успевает в реальном времени).
- Сервер: тот же модуль (plain three.js + opentype.js + clipper-lib, без React и без WebGL — вся работа чисто геометрическая) вызывается в API-роуте после оплаты, чтобы детерминированно построить STL из сохранённых параметров заказа — клиентской геометрии не доверяем, пересобираем с нуля из того, что реально записано в `print_orders`.
- Экспорт: `THREE.STLExporter` (из `three/examples/jsm/exporters/STLExporter.js`) — сериализация геометрии в STL не требует canvas/WebGL, штатно работает в Node.

**Шрифты — статика в репозитории, без шага конвертации.** В отличие от первоначального плана (конвертировать в typeface-JSON заранее), `opentype.js` читает обычные `.ttf`-файлы напрямую и на клиенте, и на сервере — просто кладём ~20-25 выбранных файлов шрифтов (Google Fonts, лицензия открытая) статикой в репозиторий один раз, без скрипта-конвертера и без сетевого запроса к Google в рантайме.

## Данные

```sql
create table public.print_orders (
  id uuid primary key default gen_random_uuid(),
  status text not null default 'pending' check (status in ('pending','paid','failed')),
  font text not null,
  text text not null,
  ring_at_end boolean not null default false,
  base_color text not null,
  text_color text not null,
  size text not null check (size in ('S','M','L')),
  price int not null,
  customer_name text not null,
  customer_phone text not null,
  note text,
  kaspi_payment_request_id uuid,
  base_stl_path text,
  text_stl_path text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Та же поза RLS-без-политик, что у `salon_sites`/`planner_sessions` — доступ только через service-role внутри роутов. Это не привязано ни к `profiles`, ни к обычным продавцам — чисто личный журнал заказов founder'а; авторизация админских экранов (если понадобится список заказов позже) — обычный `requireAdmin()`/`is_admin`, тот же паттерн, что у генератора сайтов салонов.

**Платёж.** Переиспользуем существующую интеграцию Kaspi Pay (`src/lib/kaspiPay/`) — создаём платёжный запрос тем же механизмом, что уже работает у Kaspi Shop × Kaspi Pay моста, `kaspi_payment_request_id` на `print_orders` ссылается на существующую таблицу `kaspi_payment_requests`. Webhook, который уже обрабатывает подтверждение оплаты Kaspi Pay, получает новую ветку: по типу/источнику запроса находит `print_orders` вместо обычного счёта и переводит его в `paid` + запускает генерацию STL.

## Вне рамок v1 (явно)

- Второй и далее товар (таблички, фигурки) — архитектура не мешает, но не строится сейчас.
- Отслеживание статуса печати/доставки.
- Многоцветный текст (больше одного цвета на надпись) или градиенты.
- Гравировка вместо рельефа.
- Произвольная загрузка своего шрифта/SVG/логотипа клиентом (у референса есть — не берём, YAGNI для личного магазина).
- Полный каталог Google Fonts (8267 у референса) — курируем ~20-25 кириллических.
- Ручная настройка миллиметровых параметров (толщина, обводка, скругление) клиентом — фиксированные константы на размер.
- Публичный список заказов founder'а (кроме Telegram-уведомления) — если понадобится, добавляется позже отдельной маленькой фичей поверх уже существующей таблицы.
