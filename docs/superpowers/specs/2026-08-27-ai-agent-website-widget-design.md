# Чат-виджет для сайта — Design

## Context

Пункт #4 согласованной очереди фич ("Делай все по порядку и качественно... Тарифы не трогай"), после доставленных «Заявок» (Kanban), «Онлайн-каталога продавца» и «Сценариев» на WhatsApp/Instagram. Все три уже отправленных канала AI-агента (Telegram/WhatsApp/Instagram) устроены одинаково — внешняя мессенджер-платформа шлёт нам вебхук. У чат-виджета для сайта продавца такой платформы нет вообще: доставка сообщений в обе стороны — полностью наша ответственность.

## Решения из брейншторма

- **Доставка ответа агента**: polling каждые 5 секунд — тот же приём, что уже работает для подтверждения оплаты Kaspi Pay (`/view/[token]`), проверенный на Vercel Hobby без новой инфраструктуры (WebSocket/Supabase Realtime сегодня нигде в кодовой базе не используется — не выбран сознательно, ради консистентности и нулевого нового риска).
- **Антиспам**: лимит сообщений на посетителя (id из `localStorage`) в минуту на эндпоинте отправки — публичный ключ виджета виден в исходном коде любому, кто откроет сайт продавца (нормально для встраиваемых виджетов, как у Intercom/Crisp), значит нужен базовый предохранитель от прямых вызовов API в обход самого виджета.

## Архитектура доставки

Отправка (посетитель → агент): виджет делает прямой `POST` в наш API — не вебхук, обычный вызов из браузера с публичным ключом виджета.

Получение (агент → посетитель): виджет опрашивает `GET`-эндпоинт раз в 5 секунд, пока открыто окно чата (не опрашивает, когда окно свёрнуто — экономит запросы).

Личность диалога — id посетителя, сгенерированный (`crypto.randomUUID()`) и сохранённый в `localStorage` браузера при первом открытии виджета. Играет ту же роль, что chat_id в Telegram или номер телефона в WhatsApp: `external_thread_id` для канала `website`. Диалог переживает перезагрузку страницы (тот же id из localStorage), но новое устройство/браузер — новый диалог; без входа посетителя в аккаунт это неизбежная граница v1.

## Данные

`channel = 'website'` на существующих `ai_agent_conversations`/`ai_agent_messages` — оба столбца обычный `text` без CHECK-ограничения (проверено), новое значение не требует миграции схемы этих таблиц.

Новая строка `ai_agent_channel_connections` при подключении канала на настройках:
- `channel = 'website'`.
- `external_account_id` = публичный ключ виджета (например `wgt_` + случайные 24 символа) — одновременно и то, что идёт в скрипт на сайте продавца, и routing-ключ, по которому наш API находит нужного агента.
- `access_token_enc` — у этого канала нет настоящего внешнего API и, соответственно, настоящего токена доступа; столбец `NOT NULL` по схеме, поэтому туда пишется случайное сгенерированное значение, которое НИКОГДА не используется как креденшел ни для какого исходящего вызова — явно помечено комментарием в коде, чтобы не запутать будущего читателя.
- Никакого `webhook_secret` — у виджета нет входящего вебхука, который нужно было бы подписывать.

## Приём и отправка — переиспользуем существующий пайплайн

Новый `src/lib/aiAgent/websiteWebhookHandler.ts`, по образцу уже существующих `telegramWebhookHandler.ts`/`whatsappWebhookHandler.ts`/`webhookHandler.ts` — тот же порядок приоритетов: дедуп входящего → `is_enabled`-пауза агента → пауза оператора → стоп-фраза → совпадение шаблона → совпадение триггера сценария (`flowEngine.ts`, уже общий для WhatsApp/Instagram — кнопки сценария на сайте рендерятся обычными HTML-кнопками, без платформенных ограничений по количеству вообще) → ИИ-ответ.

`sendIntoConversation` (`channelSend.ts`) получает новую ветку `channel === 'website'`: «отправка» — это просто запись исходящей строки в `ai_agent_messages`, без вызова какого-либо внешнего API (виджет сам заберёт её при следующем опросе). Это единственный канал, где отправка не требует сетевого вызова наружу.

Новые публичные (без авторизации через Supabase-сессию — посетитель сайта не залогинен в invoices.kz) эндпоинты:
- `POST /api/ai-agent/widget/message` — тело `{widgetKey, visitorId, text}`, находит подключение по `external_account_id = widgetKey`, находит/создаёт диалог по `(agent_id, channel='website', external_thread_id=visitorId)`, прогоняет через `websiteWebhookHandler.ts`.
- `GET /api/ai-agent/widget/messages?widgetKey=...&visitorId=...&since=...` — отдаёт исходящие сообщения диалога новее `since`, для поллинга.

## Виджет и скрипт встраивания

Одна строка в HTML продавца:
```html
<script src="https://www.invoices.kz/widget.js" data-key="wgt_xxxxxxxx" async></script>
```

`widget.js` — единственный публичный статический файл, при загрузке рисует плавающий пузырёк в углу страницы; клик открывает окно чата. Вся разметка и стили виджета — внутри Shadow DOM (`attachShadow`), чтобы CSS сайта продавца никогда не просачивался внутрь виджета и наоборот — стандартный приём именно для этого класса встраиваемых виджетов.

Новая карточка «Сайт» в «Каналы» на `/ai-agent/settings` (тот же MoonAI-style грид, что уже показывает Instagram/Telegram/WhatsApp): кнопка «Подключить» генерирует `external_account_id`/ключ, дальше показывает готовый `<script>`-тег с кнопкой «Скопировать».

## Антиспам

На `POST /api/ai-agent/widget/message`: не больше N сообщений на `visitorId` за 60 секунд (число уточняется при реализации по аналогии с уже принятым в этой сессии лимитом создания заказов витрины — не блокирующая деталь дизайна). Публичный ключ виджета не секрет по своей природе (как и у любого embed-виджета), поэтому лимит защищает не от подмены личности, а от накрутки платных ИИ-ответов в обход самого виджета.

## Вне рамок v1 (осознанно)

- Ограничение виджета по домену — у публичного ключа и так нет модели «секретности», ограничение по домену не добавляет реальной защиты для v1.
- Кастомизация цвета/темы/позиции виджета под бренд продавца.
- Файлы/фото от посетителя сайта.
- История диалога за пределами текущего браузера/устройства (нет входа посетителя в аккаунт).
- Push-уведомления браузеру, когда окно свёрнуто (в v1 виджет просто накапливает непрочитанные, показывает бейдж при следующем открытии).

## Тестирование

Новая чистая логика: генерация/валидация формата ключа виджета — юнит-тест. Антиспам-счётчик — юнит-тест на пороговых значениях (N-1/N/N+1 сообщений в окне). `websiteWebhookHandler.ts` использует уже протестированные общие функции (`findTemplateMatch`, `findFlowTriggerMatch`, `flowEngine.ts`) без нового покрытия сверху — как и у остальных трёх каналов, сам хендлер не юнит-тестируется, только его чистые зависимости. Живая проверка: вставить `<script>` на тестовую HTML-страницу, написать сообщение, получить ответ (шаблон/сценарий/ИИ) через поллинг в течение ~5 секунд, убедиться что диалог с иконкой «Сайт» появляется в «Переписка» и обычный ответ оператора там же доходит обратно до виджета.
