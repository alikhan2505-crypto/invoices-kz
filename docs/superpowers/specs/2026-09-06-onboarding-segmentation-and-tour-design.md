# Онбординг по сегментам + тур с подсветкой — Design

## Context

Сейчас `src/app/auth/callback/page.tsx:77` отправляет на `/onboarding` любого пользователя без `bin_iin`, а `saveStep1` там требует название компании и БИН жёстким `alert`. Реквизиты нужны только для счетов — тому, кто пришёл за демпинг-ботом, Kaspi Cashier API или AI-агентом, они не нужны вообще.

Founder выбрал **вариант B** из визуального разбора (артефакт `236fef3b-51be-4230-b208-39401c58fc18`): после регистрации сразу дашборд, реквизиты спрашиваются в момент, когда человек идёт создавать счёт. Плюс отдельно попросил **тур с подсветкой кнопок и описаниями** («как у продвинутых сайтов»), и выбрал: тур **только по дашборду**, отметка о прохождении — **в аккаунте (колонка в БД)**, не в браузере.

**Три факта, проверенных по коду перед проектированием** — они и определяют решение:

1. `saveStep1` (`src/app/onboarding/page.tsx:50`) делает **пять** дел, а не одно: валидирует реквизиты; `upsert`-ом создаёт строку профиля; обрабатывает реферальный код; вызывает `/api/onboarding/grant` за 7-дневным триалом; шлёт founder'у уведомление в Telegram. Четыре последних нужны каждому пользователю. Поэтому «просто убрать шаг 1» лишило бы всех триала.
2. `/api/onboarding/grant` (`src/app/api/onboarding/grant/route.ts`) требует **только существования строки профиля** — ни `bin_iin`, ни `company_name` ему не нужны. Значит триал можно выдавать сразу при регистрации.
3. DB-триггер `protect_profile_privileged_columns` пиннит строго заданный список колонок (`plan`, `plan_expires_at`, `is_admin`, `kaspi_wallet_balance`, `bonus_expires_at`, `trial_expires_at`, `welcome_bonus_claimed_at`, `referred_by`, `promo_granted_at`) и на INSERT принудительно обнуляет `trial_expires_at`. Новая непривилегированная колонка проходит свободно — но триал по-прежнему обязан выдавать сервис-роут после создания строки.

## Fix 1 — регистрация ведёт на дашборд

`src/app/auth/callback/page.tsx`: ветка `if (!profile?.bin_iin) → /onboarding` заменяется на ветку «профиля ещё нет».

Новый порядок для пользователя без строки профиля:
1. `upsert` в `profiles` только `{ id: user.id, email: user.email }` — без реквизитов. Строка обязана появиться до шага 3.
2. Реферальный код (`/api/referral`), если он есть в URL или localStorage — тот же вызов, что сейчас в `saveStep1`, включая `localStorage.removeItem('referral_code')`.
3. `/api/onboarding/grant` с `Authorization: Bearer <access_token>` — 7-дневный триал. Та же защита, что уже есть в `saveStep1`: если токена нет, не звать роут с `Bearer undefined`.
4. Уведомление founder'у через `/api/telegram` — fire-and-forget, как сейчас.
5. `router.push('/dashboard')`.

Для пользователя, у которого строка профиля уже есть, поведение не меняется вообще (включая существующие ветки `postLoginRedirect` и `/upgrade`).

**Что НЕ меняется:** `/create` продолжает лениво требовать реквизиты и банк и уводить за ними — это единственная реальная защита от счёта без реквизитов, и решение founder'а от 05.09 («не смягчать») остаётся в силе. Мы двигаем **момент вопроса**, а не требование.

**Страница `/onboarding` остаётся** по своему адресу и в рабочем состоянии — она перестаёт быть принудительным шлагбаумом, но не удаляется: это по-прежнему самый дружелюбный способ заполнить реквизиты, и на неё можно направлять из будущих подсказок. Дублирования логики не возникает: `saveStep1` продолжает быть idempotent (`upsert` по тому же `id`, а `grant` сам не выдаёт триал повторно — он читает существующий `trial_expires_at`).

## Fix 2 — тур с подсветкой на дашборде

Новый компонент `src/components/DashboardTour.tsx`, монтируется только на `/dashboard`.

**Механика.** Затемнение всего экрана + «дырка» вокруг подсвеченного элемента + карточка с описанием рядом. Реализация без библиотеки: элемент находится по `data-tour="<id>"`, его `getBoundingClientRect()` даёт рамку, поверх рисуется оверлей из четырёх затемнённых прямоугольников (сверху/снизу/слева/справа от рамки) — так «дырка» получается без `mask`/`clip-path`, которые в Safari ведут себя по-разному. Подсказка позиционируется под элементом, а если он в нижней половине экрана — над ним.

**Оверлей рендерится через `createPortal(..., document.body)` — это обязательное требование, а не деталь.** `globals.css` вешает `backdrop-filter` на `<main>`, и в WebKit это делает `<main>` containing block'ом для `position:fixed` и отдельным stacking context'ом. Ровно на этом 06.09 сломалась мобильная шторка: её содержимое уезжало за экран при прокрутке, а `z-index` не спасал. Любой новый фиксированный оверлей в этом проекте обязан портироваться в `<body>`.

**Шаги (4):**
1. `data-tour="products"` — сетка карточек продуктов. «Четыре продукта на одной платформе. Начните с любого — счета, приём оплат, ИИ-агент или Kaspi Bot.»
2. `data-tour="create-invoice"` — кнопка «Создать счёт». «Первый счёт можно выставить за минуту. Реквизиты компании спросим здесь же, когда понадобятся.»
3. `data-tour="menu"` — кнопка «<» в верхней панели. «Здесь всё меню: разделы и их страницы. Открытым показывается только тот раздел, в котором вы сейчас.»
4. `data-tour="wallet"` — плашка баланса. «Единый кошелёк платформы: с него списывается комиссия за счета, проверки Kaspi Bot и ответы ИИ-агента.»

Каждый шаг: «Далее» / «Пропустить» (закрывает тур целиком), последний — «Готово». Шаги 3 и 4 указывают на элементы внутри `SiteNav`/`TopUtilityBar`, поэтому `data-tour` добавляется и туда — только атрибут, без изменения поведения.

**Когда показывается.** На `/dashboard`, если `profiles.tour_completed_at IS NULL`. Отметка ставится и при «Готово», и при «Пропустить» — второй раз тур не появится ни при каких условиях, кроме ручного сброса колонки.

**Хранение.** Новая колонка `profiles.tour_completed_at timestamptz`. Пишется клиентом напрямую (`supabase.from('profiles').update(...)`) — колонка непривилегированная, триггер её не трогает, отдельный роут не нужен.

**Мобильный.** Подсказка ограничена по ширине вьюпортом с полями 12px и не выходит за края; если подсвеченный элемент выше 60% высоты экрана, карточка встаёт под ним, иначе — над.

**Доступность.** Оверлей — `role="dialog" aria-modal="true"`; Escape закрывает тур так же, как «Пропустить»; кнопки тура — минимум 44×44px по правилу DESIGN.md; при `prefers-reduced-motion` переходы между шагами без анимации.

## Out of scope (deliberate)

- Тур не выходит за пределы дашборда (решение founder'а) — никакой синхронизации через навигацию и перезагрузки.
- Мастер `/onboarding` не переписывается и не удаляется — только перестаёт быть обязательным.
- Обязательность реквизитов на `/create` не трогается.
- Никаких сторонних библиотек тура (driver.js, shepherd, intro.js) — 4 шага на одном экране не окупают зависимость, а любая из них всё равно потребовала бы того же портала из-за WebKit.
- Подсказка-«начните отсюда» на пустом дашборде вне тура — отдельная задача, здесь не делается.

## Testing

Гейт как всегда: `npx tsc --noEmit`, `npm test` (520 тестов), `npm run build`.

Живая проверка (WebKit 390×844 + десктоп) на тестовом аккаунте:
1. Новый пользователь после входа попадает **на дашборд**, а не в мастер.
2. У него есть 7-дневный триал (`trial_expires_at` заполнен) — то есть развязка не сломала выдачу.
3. Тур показывается сам, подсветка попадает по нужному элементу на всех 4 шагах, подсказка не уезжает за край экрана.
4. «Пропустить» и «Готово» оба закрывают тур и проставляют `tour_completed_at`; после перезагрузки тур не появляется.
5. Существующий пользователь (строка профиля есть) входит как раньше — ни мастера, ни тура.
6. `/create` по-прежнему уводит за реквизитами, если их нет.
