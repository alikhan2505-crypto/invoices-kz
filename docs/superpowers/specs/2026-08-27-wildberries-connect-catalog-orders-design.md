# Wildberries: Подключение + каталог + заказы/этикетки — Design

## Context

Пункт #5 согласованной очереди фич — «Мультимаркетплейс» — явно требовал декомпозиции перед спекой (сейчас весь Kaspi Bot работает только с Kaspi.kz). Первый шаг декомпозиции: с каким маркетплейсом расширяться и в каком порядке строить подпроекты.

Живое исследование официального Wildberries Seller API (не по аналогии с Kaspi, а фактчек по документации) дало ключевую находку, изменившую весь план: **репрайсер — флагманская функция Kaspi Bot — технически не переносится на WB**. У Kaspi одна карточка товара со множеством продавцов, конкурирующих ценой за верх списка («buy box»); у WB каждый продавец создаёт свою ОТДЕЛЬНУЮ карточку — самого объекта «конкурируем ценой за одно место» там нет. Более того, в сентябре 2025 WB намеренно закрыл сторонним сервисам доступ к данным о конкурентах.

Хорошая новость по остальным направлениям: у WB — в отличие от Kaspi — есть настоящий, официально задокументированный Seller API (не риск неофициального cabinet-bot), с sandbox-окружением и прозрачными лимитами запросов. Каталог, цены (только чтение), заказы, этикетки переносятся технически надёжно.

## Решения из брейншторма

- **Первый подпроект очереди**: подключение + каталог/цены (read-only) + заказы/этикетки — самый надёжный технически MVP, ничего не зависит от непроверенных возможностей WB.
- **Навигация**: новый отдельный раздел «Wildberries» в навигации, не вложенный в Kaspi Bot — разные модели данных, разная площадка.
- **Гейтинг**: раздел admin-only, тот же паттерн «ещё проверяется», что уже применён к Kaspi Bot и AI-агенту (`adminOnly` в `SiteNav.tsx`).
- **Живая проверка**: реального аккаунта продавца WB для тестирования пока нет — строим по официальной документации честно, как в своё время «Каталог НКТ» (явно помечаем непроверенное как непроверенное, не изображаем уверенность). По возможности используем sandbox-токен WB для хотя бы частичной живой проверки при сборке.

## Данные

Новая таблица `wb_connections`, свой ключ шифрования `WB_ENCRYPTION_KEY` (по установленному в кодовой базе правилу «один ключ на интеграцию», как `KASPI_SHOP_ENCRYPTION_KEY`/`AI_AGENT_ENCRYPTION_KEY`):

```sql
create table wb_connections (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references profiles(id) on delete cascade,
  token_enc text not null,
  token_expires_at timestamptz not null,
  granted_categories jsonb not null default '[]',
  status text not null default 'active' check (status in ('active', 'expired', 'error')),
  connected_at timestamptz not null default now()
);
create unique index wb_connections_user_id_idx on wb_connections(user_id);
```

`granted_categories` — какие разделы (Контент/Цены и скидки/Маркетплейс/Статистика/…) токен реально покрывает, извлекается декодированием самого JWT при подключении — не полагаемся на то, что продавец сам правильно укажет чекбоксы. `token_expires_at` тоже читается из самого JWT (WB выпускает токены на 180 дней) — используется для предупреждения за 14 дней до истечения.

**Никакой таблицы для товаров/заказов.** В отличие от Kaspi Shop (где `kaspi_shop_tracked_products` хранит состояние репрайсера — floor price, стратегия и т.д.), здесь репрайсить нечего в v1: каталог и заказы запрашиваются вживую при каждом открытии страницы, тем же способом, что уже работает для Kaspi «Заказы» (живой GraphQL-запрос без сохранения). Осознанный выбор ради стоимости: с января 2026 WB ввёл платное использование API именно для облачных сервисов вроде нашего — фоновая синхронизация была бы прямой статьёй расходов на каждого продавца независимо от того, открывает ли он вообще эту страницу; live-fetch-на-открытие стоит только тогда, когда продавец реально смотрит.

## Подключение

Продавец вставляет свой JWT-токен (кабинет WB → Настройки → «Доступ к API»). Сервер:
1. Валидирует форму токена и декодирует его (без верификации подписи — WB сам её проверит на своей стороне при первом реальном запросе; здесь декодирование только ради чтения `exp` и списка категорий из payload).
2. Делает пробный вызов (`GET https://common-api.wildberries.ru/ping`) с этим токеном — если WB отвечает не `401`, токен рабочий.
3. Сохраняет `token_enc`/`token_expires_at`/`granted_categories`, `status: 'active'`.

Настройки показывают: какие категории реально покрыты, дату истечения, предупреждение при приближении к 180 дням.

## Каталог и цены

Новая `/wildberries/products` — живой запрос к `suppliers-api.wildberries.ru` (карточки) + `discounts-prices-api.wildberries.ru`'s `GET /api/v2/list/goods/filter` (текущие цены/скидки) при каждом открытии страницы, без сохранения. Карточка товара показывает `price`/`discount`/`discountedPrice` — и явную оговорку: «Реальная цена на витрине может быть ниже — WB добавляет свою скидку (СПП), которая не отдаётся через API продавца» — честность про то, чего мы не можем показать, вместо тихого умолчания.

## Заказы и этикетки

Новая `/wildberries/orders` — живой запрос к `marketplace-api.wildberries.ru` (`GET /api/v3/orders`/`/new`). Печать этикеток — `POST /api/v3/orders/stickers` (до 100 заказов за раз), WB сразу отдаёт готовый PNG — никакой PDF-склейки как у Kaspi не нужно, продавец получает то, что WB уже сгенерировал.

## Навигация и гейтинг

Новый top-level раздел «Wildberries» (не вложен в Kaspi Bot) в `SiteNav.tsx`, тот же `adminOnly`-флаг, что уже гейтит Kaspi Bot и AI-агент — «ещё проверяется» до готовности к полноценному запуску.

## Вне рамок v1 (осознанно)

- Запись/изменение цены (асинхронная модель задач WB, обработка ошибок по каждому товару, «карантин цен» на резкое снижение) — отдельный будущий подпроект.
- Любой репрайсер — требует переосмысления под индекс цен WB («Выгодно»/«Невыгодно»), а не конкурентного демпинга; нужен отдельный исследовательский спайк, читается ли этот индекс через API вообще.
- Ниши/аналитика конкурентов — частично закрыты самим WB (сентябрь 2025) или платным «Джемом».
- Финансы, возвраты, качество/отзывы — переносятся технически чище, но по ценности ниже этого MVP; следующие подпроекты.
- Регистрация в «Каталоге решений для бизнеса» WB (нужна для нормальных лимитов вместо урезанного Basic-токена) — организационная задача основателя, не код.
- Любые тарифы/оплата за этот раздел — не обсуждается сейчас.

## Тестирование

Реального аккаунта продавца WB для живой проверки пока нет. Строим честно по официальной документации, как «Каталог НКТ» в своё время — код помечает предположения, которые не проверены вживую, вместо того чтобы изображать уверенность. Если получится получить sandbox test-токен WB без реального продавца — используем `marketplace-api-sandbox.wildberries.ru` для хотя бы частичной живой проверки заказов при сборке. Юнит-тесты — на чистой логике: декодирование JWT (категории/`exp`), расчёт «сколько дней до истечения токена».
