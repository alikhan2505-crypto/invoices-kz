# Реальные сроки оплаты по счетам — дизайн

**Статус:** одобрено, готово к написанию плана.

## Проблема

`invoices.due_date` (тип `date`) существует в схеме, но нигде не используется в коде —
ни при создании счёта, ни при отображении, ни в логике напоминаний/просрочки. `profiles.default_due_days`
(текст, default `'3'`) тоже существует и редактируется на `/profile/settings`, но тоже нигде не читается.

Вместо этого крон (`src/app/api/cron/notifications/route.ts`) и ручная кнопка «⏰ Просрочка»
(`src/app/history/page.tsx`) считают напоминание/просрочку от `created_at` с жёстко зашитыми
смещениями (3 дня / 7 дней) — независимо от того, когда реально должен быть оплачен конкретный счёт.

## Цель

Дать каждому счёту реальный, редактируемый срок оплаты (`due_date`), показывать его клиенту
и владельцу, и считать напоминание/просрочку от этой даты — при этом не ломая уже существующие
47 счетов, у которых `due_date` всегда был `NULL`.

## Архитектура

Миграция БД не нужна — колонка уже есть. Меняются только: форма создания/редактирования счёта
(проставляет и позволяет менять `due_date`), три места отображения (детали счёта, PDF, публичная
страница), и два места логики (крон, ручная кнопка просрочки) — оба получают развилку
"есть `due_date` → считаем от него; нет → старая логика от `created_at`".

## Установка срока

**Создание счёта** (`src/app/dashboard/page.tsx`): новое поле `dueDate` (`useState`), обычный
`<input type="date">` в блоке рядом с номером/датой договора (там же, где сейчас `contractDate`).
При открытии формы поле предзаполняется как `сегодня + N` дней, где `N = Number(profile.default_due_days)`,
а если это не валидное положительное число (пусто, `NaN`, ≤ 0) — фолбэк на `3` (вычисляется один раз
при загрузке профиля/сбросе формы) — пользователь может изменить дату вручную перед созданием счёта. При отправке пишется в `invoices.due_date` (или `null`, если
поле стёрли).

**Редактирование счёта** (`src/app/invoice/[id]/edit/page.tsx`): то же поле `<input type="date">`
в карточке «Договор» рядом с `contractDate`, подгружается из `inv.due_date`, сохраняется через
существующий `save()`.

Оба поля используют нативный `<input type="date">` (значение в формате `YYYY-MM-DD`, совместимо
с колонкой `date` без дополнительного форматирования).

## Отображение

- **`src/app/invoice/[id]/page.tsx`** (владелец): срок оплаты рядом с датой счёта в карточке
  деталей, только если `invoice.due_date` задан (иначе строка не показывается — не выдумываем
  дату для старых счетов).
- **`src/lib/generatePDF.ts`**: новое опциональное поле `dueDate?: string` в `InvoiceData`,
  рендерится рядом с существующей строкой `Счет на оплату №... от ...`, только если передано.
  Прокидывается из всех действующих вызовов `generateInvoicePDF` в `dashboard/page.tsx` (2 места)
  и `invoice/[id]/page.tsx` (2 места) — `dueDate: invoice.due_date ? formatDate(invoice.due_date) : undefined`
  (для мест создания — `dueDate: dueDate ? formatDate(dueDate) : undefined` из локального стейта).
  Пятый существующий вызов, в `src/app/view/[token]/page.tsx`, уже не прокидывает `kaspiPayLink`/`viewUrl`
  из прошлой фичи — расхождение до этой задачи не относится, оставляем как есть, но раз мы там же
  добавляем `dueDate`, заодно не трогаем остальные его поля.
- **`src/app/view/[token]/page.tsx`** (публичная страница): срок оплаты показывается в карточке
  счёта рядом с датой, только если `invoice.due_date` задан. В `openPDF()` (локальная генерация
  PDF на этой странице) тоже прокидывается `dueDate`.

Форматирование — через уже существующий `formatDate()` из `src/lib/date.ts`.

## Логика крона (`src/app/api/cron/notifications/route.ts`)

Обе секции (`reminderInvoices`, `overdueInvoices`) заменяются на пару запросов каждая — с `due_date`
и без:

**Напоминание** (сейчас: `created_at` от 3 до 2 дней назад):
- С `due_date`: `status IN ('sent','viewed') AND due_date = today + 1 день` — напоминание ровно
  за 1 день до срока, шлётся один раз (крон раз в сутки, дата матчится точно).
- Без `due_date` (`due_date IS NULL`): старая логика без изменений — `created_at` от 3 до 2 дней назад.

**Просрочка** (сейчас: `created_at` старше 7 дней):
- С `due_date`: `status IN ('sent','viewed') AND due_date < today - 1 день` (грейс-период 1 день
  после срока) → статус `overdue`.
- Без `due_date`: старая логика без изменений — `created_at` старше 7 дней.

Оба под-случая (с датой / без) шлют email и Telegram одинаково — существующая независимая
двухканальная логика (см. `sendTelegramNotification` вызовы в этом файле) не меняется, меняется
только SQL-условие выборки счетов.

## Ручная кнопка «Просрочка» (`src/app/history/page.tsx`)

`markOverdue()` получает ту же развилку: один `update` с `due_date < today - 1 день`,
второй `update` с `due_date IS NULL AND created_at < 7 дней назад` (текущая логика). Оба — как
сейчас, `status IN ('sent','viewed')`.

## i18n

Новый ключ `dueDateLabel` («Срок оплаты» / kk / en) в `src/lib/i18n/invoiceFlow.ts` (для форм
создания/редактирования и деталей счёта владельца) и в `src/lib/i18n/history.ts` (для публичной
страницы `/view/[token]`).

## Вне рамок

- Не меняем поведение для существующих счетов без срока — они продолжают жить по старой логике.
- Не добавляем визуальный индикатор «осталось N дней» / «просрочено на N дней» в списке `/history`
  — не запрашивалось.
- Не делаем `default_due_days` живым (пересчитывающим уже созданные счета при изменении настройки) —
  это разовое значение по умолчанию только на момент создания счёта.
