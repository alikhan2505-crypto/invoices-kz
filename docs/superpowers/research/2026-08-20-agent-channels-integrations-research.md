# Каналы и интеграции для AI-агента — исследование (2026-08-20)

По запросу «Залезь в github и узнай про интеграции и каналы для агентов».
Каталог-ориентир — MoonAI (Almaty, ~70 клиентов, листинг в маркетплейсе
bitrix24.kz — их «Звонки/SIP» в самом листинге не фигурируют, там только
Instagram/WhatsApp/Telegram/сайт + Google Sheets/AmoCRM/Notion/Altegio через
Webhook/API — т.е. часть каталога на их сайте, вероятно, витрина, а не продукт).

Строится поверх: `docs/superpowers/research/2026-08-16-whatsapp-channel-research.md`
(WhatsApp Cloud API / Embedded Signup — НЕ переписываю, только дополняю
альтернативами).

## Главное ограничение, через которое просеяно всё

Vercel Functions (fluid compute, июль 2026): Hobby 300s max, Pro 300s default /
800s max / 1800s extended beta. Нет фонового процесса, нет постоянного
соединения дольше maxDuration, 1024 файловых дескриптора на все конкурентные
исполнения, бандл 250 МБ.
→ **Любой канал, требующий постоянного сокета на КАЖДОГО тенанта
(Baileys, whatsapp-web.js, venom, MTProto-userbot, SIP-медиа) на Vercel не
живёт в принципе.** Не «медленно», не «дорого» — не работает. Только внешний
воркер (VPS/Fly/Railway) + отдельное хранилище сессий.
→ Всё, что HTTP-вебхук + HTTP-отправка (Cloud API, Bot API, наш виджет,
CRM REST), ложится на текущую архитектуру идеально.
Источник: https://vercel.com/docs/functions/limitations

Текущая архитектура, в которую всё встраивается:
- `src/lib/aiAgent/webhookHandler.ts` → `handleTenantIncoming()` — дедуп по
  `external_id`, upsert `ai_agent_conversations`, шаблоны, история пар,
  `generateAiReply`, training/active, списание кошелька. Канал-агностична
  на 90% — привязана только к Instagram-отправке в конце.
- `src/lib/aiAgent/telegramWebhookHandler.ts` — второй канал, тот же паттерн.
- `ai_agent_channel_connections` (`channel`, `external_account_id`,
  `access_token_enc`, `status`) — уже мультиканальная.
- Токены шифруются `AI_AGENT_ENCRYPTION_KEY` через `kaspiPay/crypto`.

**Рекомендация #0 (до любого нового канала):** вынести из
`handleTenantIncoming` отправку в интерфейс `ChannelAdapter { send(threadId,
text, conn) }`. Сейчас Instagram зашит в тело функции, Telegram — копия файла.
Третий канал копипастой = четыре места для правки одного бага. Effort S,
окупается на первом же новом канале.

## 1. WhatsApp

### 1a. Официальный Cloud API (Meta) — **ВЕРДИКТ: BUILD NOW**

Полностью разобран в доке от 2026-08-16. Кратко, что важно для сравнения:
Embedded Signup v4 (v2 умирает 15.10.2026), мы = Tech Provider, Business
Verification **уже пройдена**, остался App Review на
`whatsapp_business_messaging` + `whatsapp_business_management` (~24 часа),
клиент платит Meta напрямую → наши расходы на доставку = $0. Coexistence
позволяет не отбирать номер у WhatsApp Business app — критично для КЗ.
С 01.10.2026 сервисные сообщения станут платными — закладывать в цену кредита.

Библиотеки: `WhatsApp/WhatsApp-Nodejs-SDK` (274 star, официальный),
`fbsamples/whatsapp-api-examples` (288 star), `gokapso/whatsapp-cloud-inbox` (762 star).
Честно: SDK не нужен, это 3 fetch-вызова — как и в нашем `lib/instagram.ts`.

- **Effort: M** (2–3 дня; ES-попап, callback→token→`/register`→
  `/subscribed_apps`, роутинг вебхука по `metadata.phone_number_id`,
  `send()`; `handleTenantIncoming` переиспользуется почти как есть)
- **Риски:** App Review может завернуть (два отдельных видео на два
  разрешения!); лимит онбординга 10 клиентов/7 дней до Access Verification;
  per-message с октября.
- **Стоимость:** $0 нам.

### 1b. Baileys — **ВЕРДИКТ: SKIP (на Vercel), BUILD LATER только с воркером**

`WhiskeySockets/Baileys` — **10.8k star, MIT**, активнейший (коммиты 16.08.2026,
npm `@whiskeysockets/baileys@7.0.0-rc14`, ~596 зависимых пакетов). Технически
лучшая из неофициальных: чистый WebSocket, без Puppeteer/Chromium,
TypeScript.
https://github.com/WhiskeySockets/Baileys

- **Почему не сейчас:** нужен *постоянно живой* сокет на каждый номер каждого
  тенанта + persistent auth state (`creds.json`/multi-file). На Vercel это
  невозможно — максимум 300–800 с на инвокацию. Нужен отдельный воркер
  (Hetzner CX22 ~€4/мес, Fly.io ~$5–10/мес) + Redis/S3 под сессии +
  supervisor на реконнекты + UI спаривания по QR/pairing-code + очередь
  между воркером и Vercel. Это уже вторая инфраструктура, а не «ещё один
  роут».
- **ToS/баны:** прямое нарушение WhatsApp ToS, репозиторий сам пишет «not
  affiliated… we do not condone». Практика: реактивные боты (только отвечают
  на входящие) банятся редко (порядка <2% за год по отраслевым отчётам),
  проактивные рассылки — 15–30%. Наш сценарий как раз реактивный, но бан =
  клиент теряет РАБОЧИЙ номер бизнеса и приходит к нам. Для B2B SaaS с
  платящими казахстанскими МСБ это репутационно дороже, чем канал стоит.
- **Effort: L** (инфраструктура + бессрочная поддержка «меня забанили»)
- **Стоимость:** ~€5–10/мес железо + весь ваш саппорт.

### 1c. whatsapp-web.js / venom-bot — **ВЕРДИКТ: SKIP**

- `wwebjs/whatsapp-web.js` — **22.4k star, Apache-2.0**, активен (16.08.2026),

  https://github.com/wwebjs/whatsapp-web.js
- `orkestral/venom` — ~6.6k star, Apache-2.0, тот же Puppeteer-подход,
  мейнтейнер публично просит помощи («Maintainers are needed, I cannot keep
  with all the updates by myself») — красный флаг для продакшена.
- Оба — те же ToS-риски, что и Baileys, но хуже по ресурсам. Если когда-то
  делать неофициальный WhatsApp — только Baileys.

## 2. Telegram личный аккаунт (MTProto) — **ВЕРДИКТ: SKIP**

**Свежая и важная новость: `gram-js/gramjs` АРХИВИРОВАН 14 июля 2026**
(1.8k star, MIT). Мейнтейнеры перенаправляют на форк.
https://github.com/gram-js/gramjs

Преемник: **`sanyok12345/teleproto` — 309 star, MIT**, форк GramJS 2025 года,
развивается независимо, «largely compatible with GramJS», чистый JS без
нативной сборки (Alpine/ARM/serverless-friendly).
https://github.com/sanyok12345/teleproto

Почему всё равно SKIP:
1. **Vercel.** MTProto — постоянное TCP-соединение для приёма updates.
   Теоретически можно долбить `updates.getDifference` по крону, но это
   задержка в минуты, а не секунды — для чат-автоответчика бессмысленно.
   Нужен тот же внешний воркер, что и Baileys.
2. **ToS.** `core.telegram.org/api/terms` + Bot Developer ToS: обход
   рейт-лимитов и «unauthorized clients/automation tools» — прямое
   основание для перманентного бана. Бан-система Telegram в 2026
   поведенческая (тайминги, равномерность интервалов), не по ключевым
   словам. Апелляция — только @Spambot.
3. **Юридический/доверительный барьер, который убивает продукт:** чтобы
   залогинить userbot, мы должны запросить у клиента **его номер, SMS-код
   входа и пароль 2FA** и хранить сессию. Для B2B SaaS с бухгалтерскими
   документами это неприемлемый профиль риска: одна утечка `session string`
   = полный доступ к личному Telegram клиента.

У нас уже есть Telegram-боты (BotFather) — легальный, стабильный, покрывает
90% сценария. Личный аккаунт даёт только «писать со своего номера» — не
стоит ни риска, ни второй инфраструктуры.

- **Effort: L**, **риск: очень высокий**, **ценность: низкая.**

## 3. Чат для сайта (виджет) — **ВЕРДИКТ: BUILD NOW, полностью in-house**

Единственный канал без внешнего гейткипера: нет OAuth-ревью, нет банов, нет
per-message тарифа, нет посредника. Идеально ложится на Vercel и, в отличие
от всех остальных, **работает на нашем же сайте как демо агента**.

### Архитектура

```
Сайт клиента:
  <script src="https://www.invoices.kz/widget.js"
          data-agent-id="uuid" defer></script>
        │
        ├─ widget.js (одиночный ~15–25 КБ бандл, без React)
        │    создаёт <div id="ikz-agent">, attachShadow({mode:'closed'})
        │    → CSS хоста не ломает виджет, наш CSS не течёт на хост
        │    (тот же приём, что у Chatwoot; iframe оставить только под
        │     режим «строгий CSP» — в iframe хуже позиционирование пузыря)
        │
        ├─ POST /api/ai-agent/widget/session   { agentId, origin }
        │    → проверка allowed_origins тенанта (CORS + Origin-заголовок)
        │    → выдаёт короткоживущий подписанный session JWT + threadId
        │    → анонимный visitor_id в localStorage
        │
        ├─ POST /api/ai-agent/widget/message   { threadId, text }
        │    → тот же handleTenantIncoming(source:'widget')
        │    → отвечает синхронно телом ответа (LLM ~2–5 с — влезает
        │       в maxDuration с гигантским запасом)
        │
        └─ GET /api/ai-agent/widget/stream?threadId=…   (опционально)
             SSE для «оператор подключился» / стриминга токенов.
             На Vercel SSE РАБОТАЕТ — это обычный HTTP-ответ с
             прогрессивным телом, живёт до maxDuration (300 с),
             клиент переподключается. WebSocket не нужен.
```

Хранение: новый `channel='widget'` в `ai_agent_conversations`,
`external_thread_id` = наш `threadId`. Подключение тенанта —
строка в `ai_agent_channel_connections` с `channel='widget'`,
`external_account_id` = публичный `agent_id`, без токена (нечего шифровать).

### Что обязательно не забыть (это и есть вся сложность)
- **Anti-abuse:** публичный эндпоинт тратит наши LLM-кредиты. Нужен
  rate-limit по `visitor_id` + по IP + дневной потолок на агента (иначе
  один школьник сожжёт баланс клиента за ночь). Паттерн уже есть — счёт
  строк за окно, как `PAY_RATE_LIMIT` в `src/app/api/kaspi/pay/route.ts`.
- **Origin allowlist** на уровне тенанта, иначе чужой сайт вешает виджет.
- **Кеширование `widget.js`** на CDN с версией в имени файла.

Референсы: `chatwoot/chatwoot` — **36.0k star, MIT** (их SDK-виджет + shadow DOM
+ мультиканальный inbox — ближайший к нашей модели ориентир, но целиком на
Rails, берём только идеи); `papercups-io/chat-widget` + `chat-window`
(iframe-подход, проект фактически заморожен — как пример «что не делать»).

- **Effort: M** (3–4 дня: бандл виджета и его сборка, 3 роута, настройки
  в UI, rate-limit, тема/цвет)
- **Риски:** только злоупотребление кредитами и CSP на сайтах клиентов.
- **Стоимость: $0** сверх текущего Vercel.

## 4. Звонки / SIP — **ВЕРДИКТ: SKIP (не v1, вероятно не v2)**

Что реально существует:
- **`livekit/agents` — ~11.3k star, Apache-2.0**, 1.6.x, нативный SIP и
  телефонные номера с 2025 (мост через Twilio больше не обязателен),
  bring-your-own STT (Deepgram/AssemblyAI/Whisper) / LLM / TTS
  (Cartesia/ElevenLabs), MCP-тулы. Это лучший вариант на рынке.
  https://github.com/livekit/agents
- Twilio Programmable Voice / Elastic SIP Trunking — тарифы по КЗ есть
  (twilio.com/en-us/voice/pricing/kz), номер ~$1–2/мес + поминутно.
- Vonage — аналогично.

Почему не мы:
1. **Vercel не при делах вообще.** Голосовой агент — это долгоживущий
   медиа-процесс (WebRTC/RTP) с суб-секундной латентностью. Нужен
   отдельный сервис (LiveKit Cloud или свой сервер), т.е. второй
   продукт, а не фича.
2. **Язык.** Казахский и казахстанский русский в телефонном качестве
   (8 кГц, шум) — STT-качество заметно ниже, чем в чате. Ошибка распознавания
   в чате = смешно, в звонке про счёт на 2 млн ₸ = потерянный клиент.
3. **Регуляторика КЗ:** номера, запись разговоров, согласие абонента.
4. **Экономика:** ~$0.05–0.15/мин all-in (STT+LLM+TTS) + минуты Twilio.
   Против ~$0.002 за текстовый ответ. Другая юнит-экономика, другой
   тарифный план, другой саппорт.
5. **У самого MoonAI «Звонки (SIP)» не видно в маркетплейс-листинге** —
   вероятно, это позиция каталога «на витрине», а не работающий канал.
   Копировать витрину конкурента — плохая причина строить телефонию.

- **Effort: XL.** Вернуться, когда чат-каналы и CRM закрыты и
  появится выделенный инженер.

## 5. Входящий API-канал (generic) — **ВЕРДИКТ: BUILD NOW, тривиально**

Самая дешёвая строчка в каталоге. Даёт «Custom Integration» + «API» +
закрывает любой канал, который мы не поддерживаем (клиент сам приносит
Viber/MAX/Avito/свою CRM).

Форма — копия уже работающего `POST /api/kaspi/pay`:

```
POST /api/ai-agent/inbound
Authorization: Bearer <per-agent api token>
{ "thread_id": "client-42",        // произвольный ID диалога у клиента
  "text": "Сколько стоит доставка?",
  "customer_handle": "+7700...",   // опционально
  "external_id": "msg-991",        // для дедупа, опционально
  "callback_url": "https://..." }  // опционально, для асинхронного ответа

200 { "reply": "Доставка по Алматы 1500 ₸…", "urgent": false }
```

Переиспользуем один в один: `loadConnectionByApiToken`-паттерн
(`src/lib/kaspiPay/connection.ts`), rate-limit по окну, и сам
`handleTenantIncoming` с `source:'api'` — но с адаптером `send()`,
который вместо HTTP-вызова наружу просто возвращает текст в тело ответа
(или POST-ит на `callback_url`, если ответ долгий).

- **Effort: S** (~0.5–1 день). **Риски:** нет. **Стоимость:** $0.

# ИНТЕГРАЦИИ

## 1. AmoCRM + Kommo — **ВЕРДИКТ: BUILD LATER (REST — да, Chats API — нет)**

Это одна платформа: amoCRM = российский бренд/домен, Kommo =
международный. **API v4 идентичен**, отличается только базовый хост
(`<subdomain>.amocrm.ru` / `.kommo.com`) — один клиент покрывает оба, что
удваивает рынок за ту же работу.

**Важное различие, которое надо решить до кода:**
- **(A) CRM REST API v4 + OAuth2** — «агент создал сделку/контакт из
  диалога». `POST /api/v4/leads`, `/contacts`, `/leads/{id}/notes`;
  webhooks на смену статуса. Это то, чего реально хотят клиенты.
  **Делаем это.**
- **(B) Chats API (amojo)** — «агент живёт ВНУТРИ Kommo как источник
  сообщений». Технически: регистрация канала → `scope_id` + `secret`,
  каждый запрос подписывается `X-Signature` (SHA1 от payload на ключе
  канала). **Проблема: с 2026 регистрация канала больше не self-service —
  только заявка в поддержку Kommo, ревью 1–3 рабочих дня.** Плюс мы
  становимся не самостоятельным продуктом, а плагином внутри чужого
  инбокса. **Пропускаем.**
  https://www.kommo.com/developers/content/chats/connecting-a-chat-channel/

**Библиотеки (все маленькие — честно оценивая, проще написать свою fetch-обёртку на ~200 строк):**
| Репозиторий | star | Лицензия | Заметки |
|---|---|---|---|
| [`shevernitskiy/amo`](https://github.com/shevernitskiy/amo) | 12 | MIT | Лучший по покрытию: почти все модули, авторефреш токена, обработка вебхуков, типизировано, Deno+Node ≥18. Мало звёзд ≠ плохо, но bus factor = 1 |
| [`sipuni/node-amocrm`](https://github.com/sipuni/node-amocrm) | ~20 | MIT | API v4, `amoApi.leads.create()` |
| [`ostapyrih/Kommo`](https://github.com/ostapyrih/Kommo) | <10 | MIT | OAuth + v4, совсем свежий |

**Рекомендация:** взять `shevernitskiy/amo` как справочник по эндпоинтам,
но реализовать свои 5 вызовов (OAuth exchange, refresh, create lead, create
contact, add note) — иначе тащим неподдерживаемую зависимость в
финансовый продукт.

- **Auth:** OAuth2 (интеграция создаётся клиентом в своём аккаунте:
  Настройки → Интеграции → «Создать интеграцию», выдаёт client_id/secret;
  публичная интеграция в маркетплейсе — отдельная модерация).
- **Effort: M** (2–3 дня на REST + UI подключения; шифрование токенов —
  готовый паттерн)
- **Риски:** OAuth-токены протухают (refresh обязателен, у нас уже есть
  `markTokenExpiredIfUnauthorized`-паттерн); ru-домен и платежи.

## 2. Битрикс24 — **ВЕРДИКТ: BUILD NOW (входящий вебхук)**

Самая дешёвая CRM-интеграция из всех и, вероятно, самая востребованная в КЗ
(bitrix24.kz — живой локальный рынок; **MoonAI листится именно там**).

Три уровня, идти надо снизу:
1. **Входящий вебхук (local webhook)** — клиент в своём портале создаёт
   вебхук, копирует URL вида
   `https://portal.bitrix24.kz/rest/1/<token>/`, вставляет к нам в
   настройки. Мы дёргаем `crm.lead.add`, `crm.contact.add`,
   `crm.timeline.comment.add`. **Ни OAuth, ни модерации, ни маркетплейса.
   Настройка за 5 минут.**
2. **Локальное приложение** (OAuth) — если нужны события портала.
3. **Приложение в Маркетплейсе** — не столько интеграция, сколько **канал
   дистрибуции**: там уже сидят и MoonAI, и Wazzup. Отдельная задача
   маркетинга, но с прямой выручкой.

Официальный SDK: [`bitrix24/b24jssdk`](https://github.com/bitrix24/b24jssdk)
— **19 star, MIT, официальный**, поддерживает и `B24Hook` (вебхук), и OAuth 2.0
с авторефрешем на сервере. Звёзд мало, но это вендорский код.
Документация: https://apidocs.bitrix24.com/local-integrations/local-webhooks.html

- **Effort: S** (~1 день на вебхук-вариант)
- **Риски:** вебхук-токен = полный доступ к CRM клиента → шифровать как
  всё остальное; лимит REST ~2 запроса/сек на портал.

## 3. Google Sheets — **ВЕРДИКТ: BUILD NOW**

- Библиотека: [`googleapis/google-api-nodejs-client`](https://github.com/googleapis/google-api-nodejs-client)
  — официальная, Apache-2.0, ~12k star. Чистый HTTP → **на Vercel работает

- **Auth: service account, и это ключевое упрощение.** Клиент просто даёт

  (`agent-sheets@<project>.iam.gserviceaccount.com`) на свою таблицу.

- **Квоты:** 300 read-запросов/мин на проект, 500 запросов/100 с на проект
  и 100 на пользователя. Для «агент пишет строку с лидом» — на порядки
  запаса. ВНИМАНИЕ: Google анонсировал, что превышение квот станет **платным
  позже в 2026** — следить.
  https://developers.google.com/workspace/sheets/api/limits
- Сценарий: agent-функция `append_lead_to_sheet(name, phone, request)` →
  `spreadsheets.values.append`.
- **Effort: S** (~1 день). **Стоимость: $0** в пределах квот.

## 4. Google Calendar — **ВЕРДИКТ: BUILD LATER**

Технически то же `googleapis`, НО есть жёсткая ловушка:
**service account НЕ может приглашать участников без Domain-Wide
Delegation** («Service accounts cannot invite attendees without
Domain-Wide Delegation of Authority»). А DWD доступна только в Google
Workspace-домене клиента и требует доступа админа домена — для
казахстанского МСБ на личной gmail-почте это нереально.

→ Значит нужен **полноценный OAuth с consent-экраном**, а scope Calendar —
**sensitive**, что означает **верификацию приложения в Google** (недели
переписки, политика конфиденциальности, демо-видео; при restricted-scopes
ещё и ежегодный security assessment). Это дороже, чем сама фича.

Обходной путь для v1, если очень нужен «агент записывает на приём»:
service account создаёт событие в **своём** календаре и шарит его, либо
пишем запись в Sheets + шлём уведомление в Telegram владельцу. 80% пользы
за 5% усилий.

- **Effort: M (код) + L (верификация Google)**
- **Риски:** ревью Google — единственный пункт во всём списке, где сроки
  не под нашим контролем и измеряются неделями.

## 5. Kaspi — **ЭТО НАШЕ ГЛАВНОЕ ПРЕИМУЩЕСТВО, РАЗДЕЛИТЬ НА ДВА**

### 5a. Kaspi Pay как функция агента — **ВЕРДИКТ: BUILD NOW, ТОП-ПРИОРИТЕТ**

MoonAI пишет «Kaspi Pay» в каталоге как интеграцию с внешним сервисом.
**У нас это не интеграция — это внутренний вызов.** Уже работает:
- `POST /api/kaspi/pay` — Bearer-токен тенанта, `{amount, order_id,
  callback_url}`, проверка баланса кошелька, комиссия 2%
  (`computeCommission`), rate-limit 20/мин, `kaspi_payment_requests`
- `src/lib/kaspiPay/client.ts` → `createPayment()`
- `loadConnectionByApiToken` / `connection.ts` — подключение тенанта
- `POST /api/kaspi/pay/status`, крон `/api/cron/kaspi-poll`, сверка
  выписки (`acquiringMatch.ts`, `historyMatch.ts`)

**Что надо построить: не интеграцию, а слой function-calling у агента.**
Сейчас `generateAiReply` возвращает только текст. Нужно:
1. Дать модели tool `create_kaspi_payment({ amount, description })`.
2. В `handleTenantIncoming` при tool-call вызвать **напрямую**
   `createPayment()` для kaspi-подключения того же `agent.user_id`
   (не через HTTP-роут — тот же процесс, тот же Supabase, никакого
   собственного токена).
3. Вернуть ссылку на оплату в текст ответа, записать `order_id` в
   `ai_agent_messages`.
4. Владельцу — уведомление о выставленном счёте (`createNotification` +
   `sendTelegramNotification` уже подключены в `webhookHandler.ts`).

Это фича, которую конкурент физически не может скопировать быстро: у него
нет ни Kaspi-подключений клиентов, ни кошелька, ни сверки выписок.
Формулировка для лендинга: **«Агент не просто отвечает — он выставляет
счёт в Kaspi прямо в переписке и видит, что он оплачен».**

Побочный эффект: каждый выставленный агентом счёт = 2% комиссии Kaspi Pay
**сверх** списанных AI-кредитов. Канал начинает зарабатывать дважды.

- **Effort: S–M** (1–2 дня; главное — аккуратный function-calling слой и
  подтверждение суммы, чтобы модель не выставила счёт на 10 000 000 ₸ по
  галлюцинации → **обязателен потолок суммы на агента и режим
  «черновик счёта на подтверждение владельцу»**)
- **Риски:** галлюцинация суммы (митигируется потолком + подтверждением);
  всё остальное уже протестировано в проде.

### 5b. Проверка Kaspi-чеков — **ВЕРДИКТ: BUILD LATER, и не так, как MoonAI**

**Официального публичного API у Kaspi для проверки чеков НЕТ.** Найдено:
- QR на фискальном чеке кодирует ссылку вида
  `https://receipt.kaspi.kz/api/fiscal/receipt/{transaction-id}`; сам QR
  содержит только ID, данные подтягиваются с сервера Kaspi в момент
  проверки. Эндпоинт **недокументированный**, им пользуются сторонние
  сервисы (proverkacheka.kz, aipay.kz) — то есть это серая зона: могут
  закрыть, зарейтлимитить, поменять формат без предупреждения.
- GitHub по Kaspi — всё **мерчант-сторона, не проверка чеков**:
  [`burcev-alex/kaspi-qr-sdk`](https://github.com/burcev-alex/kaspi-qr-sdk)
  (PHP, Kaspi QR платежи), [`abdymazhit/kaspi-merchant-api`](https://github.com/abdymazhit/kaspi-merchant-api)
  (Go, Merchant API, без зависимостей),
  [`sultanlive/kaspi-pay-api`](https://github.com/sultanlive/kaspi-pay-api),
  [`bazarbaykz/apipay-docs`](https://github.com/bazarbaykz/apipay-docs)
  (сторонний REST-посредник ApiPay.kz с OpenAPI-спекой).
- Технически «клиент прислал PDF-чек» требует: скачать файл → PDF в
  растр → декодировать QR (zbar/opencv-класс) → HTTP к receipt.kaspi.kz.
  Растеризация PDF + нативный декодер QR на Vercel — тяжело по бандлу
  (250 МБ) и по времени.

**Наш путь лучше:** в 90% случаев клиент присылает чек об оплате
**нашему же** тенанту. У нас уже есть синхронизация операций Kaspi
(`kaspi-poll` крон, `historySync.ts`, `acquiringMatch.ts`,
`historyMatch.ts`). Значит агент может проверять оплату **по нашей
собственной базе операций** — по сумме/времени/последним цифрам — вообще
не трогая недокументированный эндпоинт Kaspi и не парся PDF. Точнее,
быстрее, легально, и снова недоступно конкуренту.

- **Effort: M** (для «сверки по своей выписке»), **L** (для полноценного
  парсинга QR из PDF — только через внешний воркер)
- **Риски:** серый эндпоинт может отвалиться в любой день — не строить на
  нём обещания в тарифе.

## ТОП-3 КАНАЛА

1. **WhatsApp Business Cloud API (Embedded Signup v4).** Business
   Verification пройдена, остался App Review ~24 ч. Чистый HTTP →
   идеально ложится на Vercel и на существующий Instagram-паттерн.
   Расходы на доставку несёт клиент (Tech Provider). Это канал №1 по
   спросу в Казахстане, и он у нас почти в руках.
2. **Чат для сайта — свой виджет.** Единственный канал без гейткипера,
   без банов, без per-message тарифа. script tag → shadow DOM → REST
   (+SSE). Даёт «Чат для сайта» из каталога MoonAI и одновременно
   работает демо-стендом агента на нашем же лендинге.
3. **Generic inbound API.** Полдня работы, копия
   `POST /api/kaspi/pay` по форме. Закрывает сразу «API» и
   «Custom Integration (webhooks)» и снимает давление по всем экзотическим
   каналам: клиент приносит свой — мы поддерживаем.

*Заглушка сверху:* **Wazzup** как аггрегатор для тех, кто не уйдёт с
личного номера WhatsApp — покупаем, а не строим.

## ТОП-3 ИНТЕГРАЦИИ

1. **Kaspi Pay как функция агента.** Не интеграция, а раскрытие того, что
   уже работает в проде (`/api/kaspi/pay`, кошелёк, сверка). Агент
   выставляет счёт прямо в диалоге и подтверждает оплату. Некопируемо
   конкурентом, приносит 2% комиссии сверх AI-кредитов, effort S–M.
2. **Битрикс24 через входящий вебхук.** ~1 день, ноль OAuth, ноль
   модерации, живой локальный рынок bitrix24.kz (где уже сидит MoonAI —
   и где стоит появиться в маркетплейсе следом).
3. **Google Sheets через service account.** Один день, ноль
   OAuth-верификации (клиент просто шарит таблицу нашему сервисному
   e-mail), квоты на порядки выше нужного. Самая частая просьба «выгружай
   лиды куда-нибудь» закрывается почти бесплатно.

*Следующая за ними:* AmoCRM/Kommo REST v4 — один клиент на два бренда,
удваивает адресуемый рынок за ту же работу.

## Осознанные «нет» и почему это правильно

Мы не делаем неофициальный WhatsApp и не делаем личный Telegram. Не потому
что сложно — Baileys (10.8k star, MIT) отличная библиотека — а потому что оба
требуют второй инфраструктуры вне Vercel, оба нарушают ToS платформ, и оба
в случае бана отнимают у клиента его **рабочий номер** или **личный
аккаунт**. Для продукта, который выставляет счета и держит доступ к Kaspi,
это несовместимый профиль доверия. Каталог конкурента длиннее — но у нас
есть Kaspi, а у него нет.
